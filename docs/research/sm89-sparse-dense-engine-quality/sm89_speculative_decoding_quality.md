# Speculative decoding quality on sm_89 (Ada), BF16 reference

## Which speculative decoding methods are lossless (MTP, DFlash, DSpark, n-gram) versus approximate, under a BF16-quality target on sm_89?

### Takeaway
With a target-model verifier, MTP, DFlash, DSpark, and n-gram are generally presented as lossless/speculation-verified methods: accepted tokens are those the target model would produce under the same decoding rule (exact-match/greedy or distribution-preserving rejection sampling). Approximate/lossy behavior arises only from non-standard verifiers (e.g. vLLM FLy), omitted/incorrect verification, or evaluation regimes that change sampling/model settings rather than from the drafting method itself.

### Cited Findings
- DFlash is described as speculative decoding with parallel verification by the target LLM: "employs a lightweight draft model to speculate a sequence of future tokens, which are then verified in parallel by the large target model. While this approach achieves lossless acceleration..." and "DFlash achieves over 6× lossless acceleration across a range of models and tasks..." — [DFlash: Block Diffusion for Flash Speculative Decoding (arXiv HTML)](https://arxiv.org/html/2602.06036).
- The DFlash paper abstract states: "Experiments show that DFlash achieves over 6x lossless acceleration across a range of models and tasks..." — [arXiv:2602.06036](https://arxiv.org/abs/2602.06036).
- vLLM documents speculative decoding as a latency optimization and separately lists a lossy verifier: "Adaptive Verification" and "FLy Verification (Lossy)" appear as speculative-decoding sub-features; "Lossless guarantees of Speculative Decoding" states "speculative decoding aims to enhance inference efficiency while maintaining accuracy" and that "vLLM’s implementation of speculative decoding is algorithmically validated to be lossless" for its standard rejection sampler, while warning "FLy deliberately relaxes verification and is not distribution preserving." — [vLLM speculative decoding README (raw)](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- vLLM lists n-gram as a supported speculative method alongside model-based methods (EAGLE, MTP, draft model, suffix): "simpler methods such as n-gram and suffix decoding provide modest speedups..." — [vLLM speculative decoding README (raw)](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- SGLang documents speculative decoding options including "EAGLE-2/EAGLE-3, MTP, UNO, DFLASH, classic draft-model decoding, and an NGRAM-based variant" and describes MTP as "Uses speculative workflow; draft path may be auto-handled for some models" in its method table — [SGLang Speculative Decoding docs](https://docs.sglang.io/docs/advanced_features/speculative_decoding.md).
- SGLang's DSpark blog states DSpark's serving integration delivers "lossless speculative speedups out of the box, at temperature 0 and above" in the linked PR summary reproduced in search results/context and describes temperature>0 support via "shared target-only speculative rejection sampling primitive" (same family as DFLASH) in PR text surfaced by search — [DSpark in SGLang (LMSYS blog)](https://lmsys.org/blog/2026-07-06-dspark-sglang/), corroborated by [sglang PR #29538 search snippet](https://github.com/sgl-project/sglang/pull/29538/files).
- Jetson AI Lab tutorial states: "Speculative decoding is a lossless way to accelerate the decode phase of LLM inference... The target model still makes the final decision at every position, so speculative decoding does not reduce output quality. Under deterministic decoding, it produces the same answer the target model would have produced without speculation. When sampling is enabled, it preserves the target model’s output distribution." — [Speculative Decoding on Jetson: MTP, DFlash, and DSpark](https://www.jetson-ai-lab.com/tutorials/speculative-decoding).
- NInfer-4090 README describes MTP speculative drafting/acceptance in benchmark rows (e.g. "100% draft acceptance", "88.0% draft acceptance") as throughput/acceptance measurements, not as quality-changing output — [UDPSendToFailed/ninfer-4090 README](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/README.md).

### Inferences
- For BF16-quality parity on sm_89, the key implementation invariant is target-side verification/rejection sampling over the same target logits/distribution as non-speculative BF16 decoding; drafter precision/architecture (MTP head, diffusion drafter, n-gram proposer) affects acceptance/speed, not correctness when verification is implemented correctly.
- "Lossless" in vendor/engine materials should be read as output-distribution or exact-verification equivalence relative to the target decode policy, not "no numerical drift anywhere in the stack"; BF16 kernels, attention backends, and sampling code paths can still introduce framework-level nondeterminism unless separately controlled.

### Gaps
- No primary source found that gives a formal side-by-side correctness proof matrix for MTP vs DFlash vs DSpark vs n-gram specifically on sm_89/Ada kernels (BF16 MMA path, FA kernels, paged KV quantization interactions).
- No direct evidence found that any listed method is intentionally approximate by design except vLLM FLy; DSpark's exact verification guarantees depend on engine/runtime path (temperature/sampling/rejection-sampling support) and were not fully auditable from fetched pages alone.

## What are the acceptance rates and quality implications for each method (MTP, DFlash, DSpark, n-gram)?

### Takeaway
Acceptance is highly workload-, model-, context-, temperature-, and tuning-dependent. Reported data show: MTP acceptance can be very high in favorable cached/greedy regimes (e.g. NInfer-4090 MTP7 rows up to 100% / 8.00 tok per round, 88% / 7.11 on prompt-cached case) but much lower on cold/other settings; DFlash/DFlash2 often reports multi-token average acceptance (τ) and several-x speedups with lossless verification; DSpark emphasizes confidence-driven variable verify length and can trade or optimize accepted work under load; n-gram acceptance is workload-dependent and typically strongest on repetitive/templated text (no Ada-specific acceptance table found).

### Cited Findings
- NInfer-4090 standard benchmark matrix on RTX 4090 (`sm_89`) reports: Deep Context MTP7 (`pp32768+tg128`, greedy, `rk4v4-e8`) `272.5 ± 0.7 tok/s`, "100% draft acceptance (8.00 tok/round)"; Prompt-Cached MTP7 (`pp2048+tg128`, greedy, INT8 KV) `220.8 ± 23.5 tok/s`, "88.0% draft acceptance (7.11 tok/round)"; Prompt-Cached MTP7 with `rk4v4-e8` `226.0 ± 23.2 tok/s`, "88.0% draft acceptance (7.11 tok/round)"; Cold Bench Corpus MTP4 (`tg128`, greedy, `rk4v4-e8`) `79.5 ± 8.7 tok/s`, "28.4% acceptance"; Baseline MTP0 `51.9 ± 2.2 tok/s` — [UDPSendToFailed/ninfer-4090 README](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/README.md).
- DFlash paper reports: "achieves over 6× lossless acceleration across a range of models and tasks, delivering up to 2.5× higher speedup than the state-of-the-art speculative decoding method EAGLE-3" and shows average acceptance length (τ) / speedup tables (e.g. Qwen3-4B/8B instruct, temperature 0 averages ~4.86–4.91× speedup, τ ~6.49–6.54 in Table 1 excerpt) — [DFlash arXiv HTML](https://arxiv.org/html/2602.06036).
- DFlash paper states drafting is conditioned on target hidden features and verified by the target model; acceptance length scales with draft quality/depth and block design (ablations in paper) — [DFlash arXiv HTML](https://arxiv.org/html/2602.06036).
- Jetson AI Lab reports measured examples: "On Jetson AGX Thor, using MTP with a speculative depth of 3 increased Qwen3.8 27B decode throughput from roughly 13 tokens/s to 35 tokens/s in our testing" and "Nemotron 3.5 Lightning reached 115 tokens/s with DSpark depth 4" in their Jetson testing; recommends starting depths MTP 3, DFlash 15, DSpark 4 — [Speculative Decoding on Jetson](https://www.jetson-ai-lab.com/tutorials/speculative-decoding).
- SGLang DSpark blog explains acceptance/budget interaction: "DSpark attacks both ends — a semi-autoregressive block drafter... and a variable per-request verify length driven by the draft model’s own confidence, which stops verifying tokens the workload is unlikely to accept"; mixed-workload example shows per-dataset verify windows/ceilings and utilization differing by acceptance difficulty (gsm8k/arena-hard/poetry) — [DSpark in SGLang](https://lmsys.org/blog/2026-07-06-dspark-sglang/).
- vLLM method guidance (qualitative) states "EAGLE/MTP/Draft model: High gain at low QPS... N-gram: Low to medium gain" and notes real gains depend on model family, traffic, hardware, sampling — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- SGLang NGRAM section notes: "retrieves draft tokens from an ngram cache built from previously generated tokens, and then verifies them with the target model" (CUDA-only in SGLang docs) — [SGLang Speculative Decoding docs](https://docs.sglang.io/docs/advanced_features/speculative_decoding.md).

### Inferences
- For a quality-focused BF16 engine, acceptance rate is primarily an efficiency metric when verification is correct; however, higher acceptance reduces exposure to scheduling/verification overhead and can make latency/jitter targets easier to meet without changing decode policy.
- DSpark's confidence-driven trimming optimizes verified work against predicted acceptance/cost; in "cap-accept" style evaluation (as described by SGLang blog) one can separate quality-equivalent committed output from missed-opportunity ceiling, which is useful for sm_89 validation.
- N-gram is likely the least predictable for general assistant/reasoning workloads but can be attractive for repetitive prompts/logs/code templates; absence of Ada-specific n-gram acceptance data means it should be benchmarked against BF16 baseline on target workloads.

### Gaps
- No peer-reviewed, sm_89-specific acceptance/quality comparison across MTP, DFlash, DSpark, and n-gram on the same model/prompts/sampling/BF16 baseline was found.
- Limited primary quality metrics beyond "lossless"/output equivalence claims (e.g. exact-match rates vs non-spec BF16 under stochastic sampling, long-context drift studies) were found for Ada deployments.
- TokenSpeed acceptance/quality numbers on Ada/sm_89 were not located in fetched primary sources.

## How do leading engines implement speculative decoding on sm_89 (NInfer MTP, UDPSendToFailed MTP+DFlash, SGLang DSpark, vLLM DFlash)?

### Takeaway
On sm_89, implementations range from specialized single-GPU engines (NInfer/UDPSendToFailed fork with native MTP and DFlash paths, Ada-targeted kernels/artifacts) to general serving frameworks (SGLang, vLLM) adding DFlash/DSpark/MTP integrations with backend/kernel constraints. Production quality depends on verifier correctness, backend attention/kernel selection, and feature compatibility (vision, quantized KV, prefix cache, concurrency).

### Cited Findings
- **NInfer / UDPSendToFailed/ninfer-4090:** "specialized, high-performance C++20/CUDA inference engine for Qwen3.8-27B on a single 24 GB NVIDIA GeForce RTX 4090 (`sm_89`)" with official groupwise `.ninfer` artifact loading, OpenAI/Anthropic APIs, native Ada Lovelace MMA tensor core execution, async double-buffered DMA staging, paged KV caching with 2-bit/4-bit lattice/cylinder quantization, CUDA graphs, ReplaySSM, compatible-prefix reuse; reports MTP0/3/4/7 decode benchmarks and DFlash-related options in docs — [ninfer-4090 README](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/README.md).
- **UDPSendToFailed/ninfer-4090 serving options:** `--spec mtp|dflash` selects speculative backend (off by default), `--draft-tokens N` with "MTP `1..5`; DFlash `1..15`", speculative residency frozen at startup; DFlash stated as "35B-A3B text-only and cannot be combined with `--vision`"; `--lm-head-draft` loads optimized proposal head — [ninfer-4090 docs/serving.md](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/docs/serving.md).
- **NInfer behavior/quality-relevant notes:** speculative decoding "does not change protocol output shapes, stop behavior, or usage accounting"; if stop truncates a multi-token MTP/DFlash round, Engine commits exact accepted target prefix for compatible reuse; prefix reuse/turn checkpoints distinguish `full_reset`, `append_frontier`, `restore_turn_checkpoint` and can skip vision for matched multimodal prefixes — [ninfer-4090 docs/serving.md](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/docs/serving.md).
- **SGLang DFlash:** docs specify `--speculative-algorithm DFLASH` with required `--speculative-draft-model-path`, `--speculative-num-draft-tokens` / `--speculative-dflash-block-size`, optional `--speculative-draft-window-size`; includes DP attention support constraints on NVIDIA CUDA ("Set `--enable-dp-lm-head`...", "Pipeline parallelism and DP combined with context parallelism are not supported"), draft execution/CUDA graph behavior notes — [SGLang Speculative Decoding docs](https://docs.sglang.io/docs/advanced_features/speculative_decoding.md).
- **SGLang DSpark:** DSpark serving integration described in LMSYS blog/PR context as block drafter with confidence head and sequential temperature scaling, confidence scheduler, ragged per-request verify, full CUDA graphs over variable-length verify, overlap-aware speculative path; "lossless speculative speedups out of the box, at temperature 0 and above" and temperature>0 rejection-sampling handling described in PR text surfaced — [DSpark in SGLang](https://lmsys.org/blog/2026-07-06-dspark-sglang/).
- **vLLM DFlash/speculative methods:** vLLM supports DFlash/MTP/EAGLE/n-gram/suffix/etc. via `--speculative-config` (e.g. `"method":"dflash"` or `"mtp"`, `num_speculative_tokens`, draft model fields) and documents lossless guarantees for standard rejection sampler; method-specific docs referenced (dflash.md, mtp.md) though not all fetched in detail — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- **Jetson AI Lab usage examples (vLLM/llama.cpp):** shows MTP (`"method":"mtp"`), separate Gemma 4 assistant for MTP, DFlash (`"method":"dflash"` + companion model, start depth 15), DSpark (`"method":"dspark"` + companion, start depth 4), and notes "llama.cpp does not support DSpark yet" — [Jetson Speculative Decoding tutorial](https://www.jetson-ai-lab.com/tutorials/speculative-decoding).

### Inferences
- For a quality-focused sm_89 engine targeting BF16 reference, NInfer-style dedicated implementations can tightly control artifact/KV/graph behavior for one GPU/model family, while SGLang/vLLM provide broader model/method coverage but require careful backend/version selection to preserve correctness and comparable numerics.
- Engine "support" on Ada does not imply identical quality/perf behavior across all kernels/backends; attention backend (FA/TRT/FlashInfer), KV dtype/quantization, prefix caching, and speculative overlap/scheduling can change acceptance and runtime characteristics.

### Gaps
- No authoritative matrix found listing exact vLLM/SGLang DFlash or DSpark kernel/backend support and validation status specifically for `sm_89` BF16 (Ada 4090) across released versions.
- Insufficient primary documentation fetched on vLLM's concrete DFlash implementation details for Ada (`docs/features/speculative_decoding/dflash.md` not fetched directly).

## What are the hardware requirements for each method on sm_89 (tensor cores, memory, drafter weights)?

### Takeaway
All methods require the target BF16 model and verification pass on Ada; requirements differ mainly in extra drafter state: MTP may use in-checkpoint heads (low/no extra model) while DFlash/DSpark need companion draft weights and KV/runtime buffers; n-gram is lightest in model weights but needs cache/state. sm_89 feasibility is dominated by 24 GB-class VRAM budgeting (target, KV cache, draft model/heads, runtime/workspace, concurrency).

### Cited Findings
- NInfer-4090 targets "single 24 GB NVIDIA GeForce RTX 4090 (`sm_89`)" for Qwen3.8-27B and reports memory/context ceilings varying by KV mode/speculation/vision (e.g. text-only no-spec `int8` KV physical max `223,000 tok`, `rk4v4-e8` `433,000 tok`; with MTP4 lower ceilings; vision further reduces) and states direct L1-cached GQA decode block table lookups support up to 1,048,576 tokens envelope — [ninfer-4090 README](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/README.md).
- NInfer serving freezes speculative residency by startup flags: omitting `--spec` loads neither backend; `--lm-head-draft` additionally loads optimized proposal head; DFlash is 35B-A3B text-only and cannot combine with `--vision` (in that engine) — [ninfer-4090 docs/serving.md](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/docs/serving.md).
- Jetson AI Lab states: "The extra memory is usually modest because the proposer is much smaller than the target model. MTP can require almost no additional model memory when its prediction heads are already included in the checkpoint..." and compares techniques/checkpoint forms (MTP usually in target, DFlash/DSpark companion checkpoints) — [Jetson Speculative Decoding tutorial](https://www.jetson-ai-lab.com/tutorials/speculative-decoding).
- DFlash repo/README describes DFlash as a lightweight block diffusion drafter and provides draft checkpoints for supported target models (installed/run as separate draft in local/server setups) — [z-lab/dflash README](https://raw.githubusercontent.com/z-lab/dflash/main/README.md).
- DFlash paper uses small draft models (e.g. 5-layer drafter in experiments) conditioned on target hidden features and discusses drafting cost/latency tradeoffs; Figure 3/text show draft cost comparisons for 1/3/5-layer DFlash vs EAGLE-3 — [DFlash arXiv HTML](https://arxiv.org/html/2602.06036).
- vLLM/SGLang require draft model paths or method-specific configs for draft-model/DFlash/standalone modes; MTP may be built-in for MTP-enabled models (per docs) — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md), [SGLang Speculative Decoding docs](https://docs.sglang.io/docs/advanced_features/speculative_decoding.md).
- vLLM explicitly notes speculative decoding can increase GPU memory usage due to draft tree/CUDA graphs/verification buffers and gives OOM tuning knobs — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).

### Inferences
- On 24 GB sm_89, BF16 target + long context + speculative drafter/KV/workspace can be tight; quality-focused configurations should budget headroom for BF16 target weights, verification activations, and any auxiliary KV (draft/target) before increasing draft window/tree depth.
- Tensor-core utilization is implicit for BF16/GEMM/attention paths on Ada, but method choice affects whether extra compute is useful (high acceptance) or wasted (low acceptance at high batch/long verify). No special non-tensor-core-only requirement was identified from sources; kernel/backend availability matters more.

### Gaps
- No precise, source-backed VRAM formulas or measured draft-weight sizes for specific DFlash/DSpark checkpoints on sm_89 BF16 targets (beyond general "lightweight/small" descriptions).
- No direct Ada/sm_89 tensor-core occupancy or kernel-level requirement comparison across MTP/DFlash/DSpark/n-gram found.

## What validation is needed to ensure acceptance rate, quality parity, and no degradation versus BF16 on sm_89?

### Takeaway
Validation should combine (1) correctness/parity tests against non-speculative BF16 decoding under matched settings, (2) acceptance/throughput telemetry per workload and context regime, and (3) stress tests for long context, batching/concurrency, prefix caching, and feature interactions. vLLM's documented lossless guarantees and SGLang's cap-accept/observability ideas provide concrete validation patterns.

### Cited Findings
- vLLM documents lossless validation approach: "Algorithmic Losslessness — vLLM’s implementation... algorithmically validated to be lossless" citing rejection sampler convergence and greedy sampling equality tests; also warns about logprob stability, floating-point precision, and batch-size/numerical stability affecting outputs across runs — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- vLLM recommends reproducible measurement via `examples/features/speculative_decoding/spec_decode_offline.py` or benchmark CLI and provides acceptance metrics docs reference — [vLLM speculative decoding README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md).
- SGLang DSpark blog describes observability for censored ceilings: `cap-accept` "verifies the full block but commits only up to the window... commits exactly what compact commits while exposing the ceiling" to distinguish good trims from lossy ones; also tracks per-request confidence/calibration metrics — [DSpark in SGLang](https://lmsys.org/blog/2026-07-06-dspark-sglang/).
- Jetson AI Lab recommends tuning and benchmarking: "run the target with speculative decoding disabled, then repeat the same request set at several depths... Keeping the target checkpoint, context length, sampling settings, concurrency, Jetson power mode, and clocks unchanged..." track throughput, ITL, TTFT, E2E latency, acceptance rate, peak memory — [Jetson Speculative Decoding tutorial](https://www.jetson-ai-lab.com/tutorials/speculative-decoding).
- NInfer serving logs/telemetry-oriented design includes exact prefix reuse reporting (`cache=`), request logs with timings/speculative counters, and states speculative decoding must not change protocol output shapes/stop behavior/usage accounting — [ninfer-4090 docs/serving.md](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/docs/serving.md).
- DFlash/NInfer/engine materials show acceptance strongly varies by mode (e.g. prompt-cached vs cold, draft tokens/window, KV dtype, context length), implying validation must cover representative operating points — [ninfer-4090 README](https://raw.githubusercontent.com/UDPSendToFailed/ninfer-4090/feat/rtx-4090-sm89-native/README.md), [DFlash arXiv HTML](https://arxiv.org/html/2602.06036).

### Inferences
- A BF16-reference quality gate on sm_89 should include: deterministic greedy equivalence tests (same prompt/template/seed policy where applicable) and stochastic distribution checks (rejection-sampler parity / statistical output comparison) versus non-spec BF16, repeated across batch sizes and long-context lengths.
- Acceptance-rate validation should be segmented by prompt cache hit/cold, context length, draft depth/window, and KV mode/quantization, because NInfer and DFlash results show large swings; "average acceptance" alone is insufficient for quality-focused service SLOs.

### Gaps
- No canonical, public sm_89-specific validation suite/checklist for MTP+DFlash+DSpark+n-gram parity against BF16 was found.
- No fetched source provided exact numeric tolerances for BF16 parity under speculative decoding on Ada (beyond general floating-point/logprob stability caveats).
